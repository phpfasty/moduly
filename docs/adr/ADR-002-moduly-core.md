# ADR-002: ModulY — агностичное ядро и forward-only миграции

- Статус: принято (2026-10-30)
- Авторы: PHP FastY

## Контекст
Серверная логика сайтов WP FastY (типы данных, корзина, заказы, согласия) должна ставиться и обновляться модулями, а данные — переживать смену темы. Плагин `wpfasty-types` при смене вида поля удалял значения (`delete_post_meta` в `Plugin::migrate()`), что недопустимо.

## Решение

### 1. Разделение
- `phpfasty/moduly` (этот репозиторий) — **только CMS-агностичное ядро PHP**: манифест, валидация, подпись, lifecycle, DI, контракты миграций и хранилища. Никаких вызовов WordPress в `src/` (архитектурный тест `tests/Architecture`).
- `phpfasty/wpmodules` — отдельный монорепо: WordPress-плагин, который ставит ядро через Composer и содержит модули (`types`, `cart`, `orders`, …). Всё WP-специфичное (options, post meta, WP-CLI, Action Scheduler, хуки) — там.
- Пакет для wordpress.org готовится позже, но код с самого начала соответствует требованиям каталога (GPL-совместимая лицензия, без загрузки исполняемого кода со сторонних серверов).

### 2. Миграции: только вперёд, идемпотентно
Ядро определяет агностичные интерфейсы; реализация хранения — в адаптере.

| Аспект | Ядро (moduly) | Адаптер (wpmodules) |
|---|---|---|
| Версия схемы | `SchemaVersionStore` (get/set по scope) | option `moduly_schema_version` = `{<theme\|pack>: N}` |
| Миграция | `MigrationInterface::up()`, классы `Migration_NNNN_<Name>` | реализации на post meta / options |
| Запуск | `Migrator` (порядок, идемпотентность, lock-порт) | батчи через Action Scheduler / WP-CLI, lock в option/transient |
| Чтение значений | `ValueReader` (default + log), `FieldAdapter`, aliases | `get_post_meta` под капотом |
| Prune | интерфейс `PruneCommand` (dry-run → report → backup → confirm) | `wp moduly types prune` |

Правила:
1. **schema_version** хранится по каждой теме/паку отдельно. Миграции — классы `Migration_NNNN_*` только с `up()`; forward-only, идемпотентны (повторный запуск — no-op), `down()` нет и удалений нет.
2. **Смена вида поля**: старое значение не трогаем никогда. Либо пишем в новый ключ (`price` → `price_v2`), либо читаем через адаптер, конвертирующий на лету. Переименование — через `aliases`: читаем новый ключ, при отсутствии — старый.
3. **Невалидные значения**: при чтении возвращается default поля + запись в лог; в БД значение остаётся. Удаление — только отдельной командой `wp moduly types prune --dry-run` → отчёт + JSON-бэкап → удаление лишь после явного подтверждения.
4. **Батчи**: миграции выполняются порциями (Action Scheduler / WP-CLI) под lock'ом; прерванный запуск безопасно перезапускается с места остановки.
5. **Тесты**: сценарий «старая схема → migrate → смена темы → возврат» — вся meta цела (count и значения байт-в-байт); статическая проверка, что в классах миграций нет `delete_post_meta`, `delete_option`, `delete_metadata`, `DELETE`-SQL.

## Последствия
- Данные никогда не теряются при обновлении или смене темы; цена — рост «осиротевших» ключей, которые видны в отчёте prune.
- Ядро переиспользуемо для других CMS; WP-часть развивается независимо в `wpmodules`.
- Лицензия AGPL-3.0-or-later (GPLv3-совместима, допускается каталогами wordpress.org).
